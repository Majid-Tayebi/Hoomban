# چرا هومبان به‌جای وردپرس؟  
# Why Hoomban Instead of WordPress?

**مخاطب:** کارفرما / تصمیم‌گیرنده غیر‌فنی  
**هدف سند:** توضیح شفاف اینکه برای کلینیک روانشناسی با دادهٔ حساس و عملیات روزانه، **توسعه اختصاصی** انتخاب درست‌تری از راه‌اندازی روی وردپرس است.  
**لحن:** حرفه‌ای، واقع‌بینانه، بدون اغراق بازاریابی توخالی.

---

## فارسی

### جمع‌بندی یک‌خطی

وردپرس برای **سایت محتوا و فروشگاه عمومی** عالی است.  
هومبان یک **نرم‌افزار عملیاتی کلینیک** است (نوبت، پرونده بالینی، آزمون روان‌شناختی، حسابداری پذیرش، نقش‌های سخت‌گیرانه). این دو مسئله یکی نیستند؛ ابزار یکی هم نباید باشد.

---

### ۱. ماهیت مسئله فرق دارد

| نیاز کلینیک | وردپرس (معمول) | هومبان (اختصاصی) |
|-------------|----------------|------------------|
| صفحه درباره ما / مقاله | ✅ قوی | ✅ دارد |
| رزرو نوبت پیچیده + ساعات متخصص | پلاگین‌های عمومی، سفارشی‌سازی سخت | ویزارد اختصاصی + قوانین کلینیک |
| یادداشت بالینی محرمانه | معمولاً در جدول‌های پلاگین یا user meta | Collection جدا + ACL سخت (منشی نمی‌بیند) |
| آزمون NEO-240 با امتیاز غیرقابل دستکاری | تقریباً ناممکن بدون کدنویسی سنگین | محاسبه و اعتبارسنجی **فقط سمت سرور** |
| نقش منشی / پزشک / نویسنده / مراجع با مرز دقیق | نقش‌های وردپرس + پلاگین؛ سوراخ زیاد | RBAC دو لایه (دیتابیس + سرور اپ) |
| پرداخت آنلاین با مبلغ غیرقابل جعل | وابسته به پلاگین و هوک‌ها | مبلغ خدمت از دیتابیس با `serviceId` |
| انطباق با حریم دادهٔ سلامت | مسئولیت روی دوش پیکربندی پلاگین‌ها | طراحی از روز اول حول PHI |

**نتیجه برای کارفرما:** با وردپرس «ظاهر سایت» را سریع می‌گیرید؛ با هومبان «عملیات کلینیک» را مالک می‌شوید.

---

### ۲. امنیت و حریم خصوصی (مهم‌ترین تفاوت)

کلینیک با **داده سلامت و هویت مراجع** کار می‌کند. در اکوسیستم وردپرس:

- هسته + تم + ده‌ها پلاگین = **سطح حمله بزرگ** و به‌روزرسانی مداوم اجباری  
- بسیاری از نشت‌ها از پلاگین‌های قدیمی یا ضعیف ACL می‌آید  
- جدا کردن «منشی ببیند شماره تماس / پزشک ببیند پرونده» در پلاگین‌های آماده معمولاً شکننده است  

در هومبان:

- قفل ارتقای نقش توسط خود کاربر  
- نوبت فقط از API سرور ساخته می‌شود  
- نتیجه آزمون برای منشی بسته است  
- پروفایل از مسیر کنترل‌شدهٔ `/api`  
- توکن احراز هویت در `localStorage` ذخیره نمی‌شود  
- فایل صوتی/پیوست روی استوریج با قانون دسترسی — نه روی هاست عمومی وردپرس  

این‌ها «تنظیمات پلاگین» نیستند؛ **قوانین محصول** هستند.

---

### ۳. کیفیت تجربه و سرعت عملیات

| موضوع | وردپرس | هومبان |
|-------|--------|--------|
| UI پنل | پیشخوان WP یا صفحه‌ساز | پنل RTL اختصاصی نقش‌محور |
| عملکرد | وابستگی به کش پلاگین و کوئری‌های سنگین | SSR هدفمند + کش لندینگ + فیلدهای محدود PB |
| جریان منشی | چند پلاگین جدا (نوبت + CRM + حساب) | میز پذیرش یکپارچه |
| موبایل کارکنان | تم/اپ جدا | همان پنل ریسپانسیو + PWA پایه |

زمان منشی و روانشناس هزینه دارد؛ یکپارچگی جریان کار مستقیم روی هزینهٔ جاری کلینیک اثر می‌گذارد.

---

### ۴. مالکیت، وابستگی و هزینهٔ واقعی

**برداشت غلط رایج:** «وردپرس رایگان است.»

هزینهٔ واقعی معمولاً این‌هاست:

- لایسنس تم/پلاگین پرمیوم  
- نگهداری امنیتی ماهانه  
- سفارشی‌سازی هر بار که فرآیند کلینیک عوض شود  
- مهاجرت دردناک وقتی پلاگین اصلی deprecate شود  
- هزینهٔ رفع باگ بین پلاگین‌های ناسازگار  

**با هومبان:**

- کد و دامنهٔ کسب‌وکار **مالکیت کلینیک / تیم شماست**  
- منطق نوبت، تعرفه، نقش‌ها و آزمون‌ها در مخزن مشخص است  
- تغییر فرآیند = تغییر کنترل‌شده در کد، نه جست‌وجوی «پلاگین جایگزین»  
- هزینه جلوتر شفاف‌تر است: توسعه + میزبانی Node + PocketBase  

برای افق ۲–۵ ساله کلینیک، هزینهٔ مالکیت نرم‌افزار اختصاصی اغلب **قابل پیش‌بینی‌تر** از جنگ پلاگین‌هاست.

---

### ۵. مقیاس و مسیر رشد

وردپرس وقتی رشد می‌کند که «محتوا و ترافیک» رشد کند.  
کلینیک وقتی رشد می‌کند که «تعداد مراجع، متخصص، خدمت، گزارش مالی و انطباق» رشد کند.

هومبان از الان برای این مسیر ساخته شده:

- نقش‌های جدید بدون شکستن ACL  
- API و OpenAPI برای اتصال آینده (اپ موبایل، بیمه، BI)  
- تست خودکار (واحد + E2E امنیتی) قبل از استقرار  
- مانیتورینگ خطا (Sentry) و rate-limit آمادهٔ production  

وردپرس می‌تواند با REST/Headless جلو برود؛ اما برای همین سطح کنترل، در عمل به **تیم توسعه اختصاصی روی وردپرس** می‌رسید — با پیچیدگی بیشتر و محدودیت پلتفرم. در آن نقطه، دیگر «مزیت سرعت وردپرس» از بین رفته است.

---

### ۶. پاسخ به نگرانی‌های متداول کارفرما

**«پس بلاگ و SEO چی؟»**  
هومبان CMS مقالات، sitemap، OG، Schema و FAQ دارد. برای کلینیک کافی و تخصصی است.

**«آیا نمی‌شد وردپرس + چند پلاگین؟»**  
می‌شد ظاهر ساخت؛ نمی‌شد بدون هزینهٔ سنگین، امنیت بالینی و امتیاز غیرقابل جعل آزمون و حسابداری میز را درست و پایدار ساخت.

**«اگر فردا نیرو عوض شد؟»**  
مستندات معماری، ADR، کاتالوگ امکانات و کد TypeScript خوانا انتقال دانش را ممکن می‌کند — شفاف‌تر از تنظیمات پراکندهٔ ۲۰ پلاگین.

**«زمان تحویل؟»**  
وردپرس برای لندینگ سریع‌تر است. برای سامانه عملیاتی کامل، مسیر اختصاصی کوتاه‌تر از «وردپرس + سفارشی‌سازی بی‌پایان» تمام می‌شود — چون دوباره‌کاری بین پلاگین‌ها حذف می‌شود.

---

### ۷. جمع‌بندی پیشنهادی برای تصمیم

| اگر اولویت شماست… | انتخاب منطقی |
|-------------------|--------------|
| فقط سایت معرفی + فرم تماس | وردپرس می‌تواند کافی باشد |
| کلینیک واقعی با پرونده، نقش، پرداخت، آزمون، میز پذیرش | **هومبان (کدنویسی اختصاصی)** |
| امنیت داده سلامت و ممیزی‌پذیری | **هومبان** |
| سرعت ظاهری هفتهٔ اول بدون زیرساخت عملیاتی | وردپرس |

**پیشنهاد:** وردپرس را رقیب هومبان نبینید؛ آن را ابزار دیگری برای مسئلهٔ دیگری ببینید. برای هومبان، انتخاب درست از روز اول **نرم‌افزار اختصاصی** بوده است.

## English

### One-line summary

WordPress excels at **content sites and generic commerce**.  
Hoomban is a **clinic operations system** (booking, clinical notes, psychometrics, desk accounting, strict roles). Different problem → different tool.

### Why custom software wins here

1. **Domain fit** — Multi-role clinical workflows and server-side NEO scoring are first-class product rules, not plugin afterthoughts.  
2. **Security posture** — Dual-layer RBAC, locked role escalation, server-only appointment writes, profile BFF, payment amounts from DB, no auth token in `localStorage`. Plugin stacks expand attack surface and weaken PHI boundaries.  
3. **Operational UX** — One RTL panel for secretary/doctor/admin instead of stitching booking + CRM + billing plugins.  
4. **Ownership** — Business logic lives in your repository; no hostage to abandoned plugins or license mazes.  
5. **Growth path** — OpenAPI, automated tests, Redis rate-limit/cache, Sentry, PWA—built for a clinic that will add staff, services, and integrations.

### Honest caveat

If the only need were a brochure + blog, WordPress would be rational.  
Once the clinic needs **confidential records, non-forgeable assessments, and desk finance**, a purpose-built stack is the lower-risk and usually lower *true* cost over a multi-year horizon.

### Decision table

| Priority | Better fit |
|----------|------------|
| Marketing site only | WordPress |
| Real clinic OS (PHI, roles, payments, tests) | **Hoomban** |
| Auditability & security of health data | **Hoomban** |
| “Looks ready this week” without ops depth | WordPress |

**Bottom line for stakeholders:** Choosing custom development for Hoomban was not preference—it was the architecture that matches clinical reality.
